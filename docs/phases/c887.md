# Process Sources on preview

Jeff and Adam process every existing Source into a copy of production on the preview server, so that the Facts the release ships with are attributed to the Sources that state them. The pipeline is the migration for everything that lives in Sources. How fast and how cheaply the producer runs belongs to the import-at-scale phase, not this one.

## Why on preview

- **Preview's replay log is what reaches production.** The backscan of ~927 Sources takes weeks and can't happen in a maintenance window. Curators decide on preview, and at cutover preview's replay log is replayed into production after the data migration.
- **Every decision a curator makes must be made on preview** (or, for a fix to the old site's data, put in a curated file under `priv/catalog_migration/`). That covers review decisions, Host-name synonyms and plants, Trait-term placements, taxonomy acceptances and declines, and edits. Work done on a local database such as `gallformers_taxogall` never reaches production unless it is redone on preview.
- **Preview needs its own Postgres** with WCVP and a production data copy (the preview environment phase). Plants are added from WCVP, and plant authorship and the replay read WCVP.

## How Sources are processed

The procedure is `runbooks/source-intake.md`: choosing what to run next, preparing the Source, and the review's steps (Names, Galls, Traits, Facts, names the producer skipped, Undo). The rules it rests on:

- **Newest first, per group of taxa.** A paper's taxonomic statement raises a question only if it is newer than the latest accepted paper for that taxon. Accepting a paper closes open questions about the same taxon from older papers as history. The order of review changes only the number of questions, never the outcome.
- **Taxonomy questions don't hold a Source's approval.** Name-resolution questions do (which organism the Source means), because Galls and Hosts can't attach without them. Questions about following a paper's placement, accepted name or synonymy go to one cross-Source queue (`/admin/review/taxonomy`). They stay there until a curator accepts or declines each, so a hard taxonomic call doesn't stall the backscan.
- **Unresolved Host names are resolved before the gall batch**, as part of the taxonomy step: add a synonym or the plant.
- **Humans approve every database change.** Nothing ambiguous is applied automatically.
- **Track coverage:** Facts confirmed by a Source, and Facts with no Source support.
- **Legacy Facts the backscan doesn't confirm stay** (Jeff, 2026-10-27). They are attributed only to the undated "Gallformers legacy data", and marked unconfirmed wherever they are shown (pages and the API). A later Source or a curator can confirm or deny them.
- **Trial batches end to end first:** a few Sources of different kinds (paper, website, research data), including a correction and a retraction.

## Before the first Sources: seed the trait terms

Trait values are categories, and each Source's own words are sub-terms placed under them. A term is placed automatically only when it is already in the term table, or when the producer and the checker place it in the same category independently. Anything else is a curator question.

So a curator reviews the ~850 existing (Source wording, value) pairs from producer output **before go-live**, so that early Sources don't flood the queue:

- `mix gallformers.import.term_candidates <dirs>` gathers the terms of producer packages (the `gall.json` files under each directory) into `trait_term_candidates`. Gathering a package again replaces its counts, a decided candidate is never changed, and terms the table already holds are reported.
- "Seed terms" on `/admin/vocabulary` (superadmins) places each candidate, marks it ambiguous, or marks it as fitting no category, singly or in bulk where the uses agree.
- Seed on preview, so that the placements reach production through the replay log (`:trait_term_edit`).

## Before publishing: the public snapshot

`priv/snapshot/tables.txt` lists `pending_trait_terms` as public, because its terms show on Gall pages. But each row also keeps its origin: `source_id`, `package_id`, `batch_id`, `queue_item_id`, `statement_ref`, and the batch's quotes (`evidence`). The package, batch and queue IDs point into tables the snapshot keeps private. The snapshot workflow publishes from production's full backup, so this must be settled before cutover. Decide what the published copy holds: drop those columns, publish a derived table, or accept them.
