Convert read-only pages from LiveView to plain controllers where that pays.

## Why

Every page was a LiveView, including read-only display pages. That brought three costs:
1. **WebSocket fragility.** Every `phx-*` binding goes inert when the socket dies (a tab idle 5–10 minutes): modals can't be dismissed, buttons stop working, forms fail silently.
2. **Memory pressure.** A long-lived process per open tab. The old Browse pages held 670 KB–1 MB of tree data per process.
3. **Double mount.** Every page load does the HTTP render plus the WebSocket connect, even for static content.

The 2026-02-18 OOM incident write-up cites this (`docs/incidents/20260218-oom-crash-bot-traffic-memory-accumulation.md`).

## What phase 1 did (on main, and still on taxogall)

- **A reconnection fix.** A `visibilitychange` listener (`assets/js/app.js`) forces an immediate WebSocket reconnect when a backgrounded tab regains focus. That fixes the dead socket for every LiveView page.
- **Hook extraction.** 11 inline hooks moved from `app.js` into `assets/js/hooks/`.
- **Five pages moved to controllers:** Privacy (`/privacy`), Filter Guide (`/filterguide`), Articles index (`/articles`, tag filtering through URL params), Article (`/articles/:slug`) and About (`/about`, its easter-egg toggle now `JS.toggle`). They are `AboutController`, `ArticlesController`, `ArticleController`, `PrivacyController` and `FilterGuideController` in `router.ex`.
- **Keys reverted** to LiveView: Keys is a growing feature (matter 85c0) that will need galleries and interactivity.

## Phase 2: undecided, needs investigation

The original plan would have converted pages with client-side filtering (genus, section, browse, search) using Alpine.js or hand-written JS. That raised concerns:
- **JS bloat and duplicated domain logic.** Genus and section search filters and sort comparators would rewrite in JavaScript what Elixir knows: how to sort names, which fields to search, common-name fallbacks.
- **The place page's map.** The `range_map` hook uses `pushEvent('navigate_to_place')`, which needs a LiveView. A shared hook would have to detect controller vs LiveView context.
- **Browse.** Tree expand/collapse and filtering over large data.
- **Gall and Host pages.** 11–13 events each: source dialogs, pagination, font size, galleries.
- **The calculus changed.** The reconnection fix addresses the dead-socket UX for every LiveView page. What's left (memory, double mount) are optimizations that may or may not matter at this scale.

Open questions:
- Is the JS duplication worth the memory and performance gains?
- Are there hybrid approaches (LiveView with reduced assigns, lazy loading) that address memory without converting?
- Does Alpine.js or similar change the equation for pages like genus and section?
- What does memory pressure look like in production: real or theoretical?

How the pages stood:

| Page | Interactivity | Concern |
|---|---|---|
| Keys index + detail | static list, growing | will need galleries, interactivity |
| Genus / Section | search + sort | duplicates domain logic in JS |
| Place | range map navigation | hook needs `pushEvent` |
| Gall / Host | dialogs, pagination, galleries | 11–13 events |
| Browse (galls, hosts, places) | tree data, search, filters | large per-process data |
| Home, Search | debounced DB search | genuinely interactive |
| ID tool | complex filters | stays LiveView |
| Admin | forms, validation, PubSub | stays LiveView |

So even the controller pages now open a WebSocket and a LiveView process. The public pages were also all rebuilt on the design system (bc0d), so the event counts above are from before that.
