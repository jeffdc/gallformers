Jeff's idea at intake (2026-11-09): move user management off Auth0, and refine permissions and roles at the same time. It replaces the dropped Auth0-based matters 0fc6 (in-app user management through the Auth0 Management API), 3f58 (unify Auth0User and User) and ec68 (permissions and roles refinement, which had no body). Nothing is designed yet.

**What exists today** (in code as of a0434bcf):
- **Auth0** handles sign-in through Ueberauth (`ueberauth`, `ueberauth_auth0`).
- **Roles** arrive as Auth0 custom claims (`https://gallformers.org/roles`) on each login: `admin`, `superadmin`, `operator`.
  - They are checked by `Accounts.admin?/1`, `superadmin?/1` and `operator?/1`, the plugs `RequireAdmin`, `RequireSuperAdmin` and `RequireOperator`, and the `GallformersWeb.Live.UserAuth` on_mount hooks.
  - A role change shows only at the user's next login.
- **Superadmins manage users in the Auth0 dashboard.** The app has no Management API integration. `/admin/users` only toggles "show on About page", and the Profile page edits display name, bio and links. A "Reset password" link to Auth0's reset flow exists.
- **Three representations of a user** (3f58), which leak the auth provider into the web layer:
  - `Accounts.Auth0User`: the session struct from Auth0 (id, email, name, nickname, picture, roles), not persisted, stored as `@current_user`;
  - `Accounts.User`: the `users` table (`auth0_id`, display_name, nickname, about_me, URLs, show_on_about) for preferences and public display;
  - `Accounts` itself, managing both plus session lifecycle, role checks and Auth0 ↔ DB sync.

  `display_name` has three meanings: `Auth0User.display_name/1` (name → nickname → email), the DB field (user-editable, synced on login), and `Accounts.db_display_name/1`. The web layer called `Auth0User.display_name` directly at 8 sites; 3 files still do.

  3f58's direction was one user identity: the web layer sees one struct and asks Accounts for everything, with the auth provider internal to Accounts.
- **Curators' audited actor:** taxogall resolves an admin's session user to a local `User` and an `Audit.Actor` (`UserAuth` `:require_admin_actor`, `curator/1`).
- **The current role decision** (Jeff, 2026-11-06, matter ec2c):
  - **admin** (curator) does everything in the curation design, including deleting Galls and taxa;
  - **superadmin** adds only Trait categories (the vocabulary) and users;
  - changing a Gallformers code without confirmation is never possible, for anyone.
- `dev_auth_bypass` logs dev in as an admin without Auth0.

**From 0fc6, the costs of building on Auth0's Management API, which moving off it would avoid:**
- an M2M app with user and role scopes, and new secrets;
- token caching (about 24 h);
- a rate limit of 2 requests a second on the free/essential tier, with 429 backoff;
- role changes delayed until the next login;
- an invite flow through `POST /tickets/password-change`.

0fc6 judged in-app user management low-ROI while the admin pool is small (2 superadmins and a handful of admins). The inflection point it named was contributor growth.

Jeff's new idea at intake, replacing the dropped Auth0-based matters.
